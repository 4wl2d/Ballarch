# Переход с Pokeball Core 1.5 на Ballarch Core 2.0

До Core 1.5 включительно Ballarch публиковался под названием Pokeball. [Предыдущая опубликованная версия, Pokeball Core 1.5.0-draft,](https://github.com/4wl2d/Pokeball/tree/1bb9e0ecca4d4d1c8b39327c93988c1b490f303e) осталась в истории Git. Core 2 заменяет привязку (binding), которую определял сам проект, меньшим контрактом runtime и исполняемыми проверками соответствия. Это руководство сопоставляет словарь 1.5 и каждый из её 44 законов с [Core 2.0](../../spec/ballarch-core-2.0.md).

## Что меняется для разработчика

1. **Один решатель вместо трёх ролей.** Разделение на Interaction, Nucleus и Resource превращается в чистый *решатель* (бывший Nucleus) и *адаптеры* на краях (бывший код Interaction и Resource). Runtime делает то, что 1.5 оставляла «привязке» каждого проекта: обрабатывает входы строго по одному, атомарно фиксирует, отправляет выходы, следит за дедлайнами и классифицирует исходы.
2. **Три входа, четыре выхода.** Шесть видов Pulse и семь видов SemanticOutput сводятся к Request, Completion и Notice (входы) и Call, Reply, Publish и Cancel (выходы).
3. **Исход определяется классом эффекта.** В 1.5 применимость `OutcomeUnknown` определял триггер закона (например, «могло выполниться»). В Core 2 runtime выбирает `Done`, `NotDone` или `Unknown` по фазе вызова и классу эффекта, записанному вместе с вызовом при фиксации (`Safe`, `Idempotent` или `NonIdempotent`). Порт Safe никогда не даёт `Unknown`.
4. **Ключи идемпотентности создаёт runtime.** В 1.5 привязка выводила ключ эффекта из `OperationId` и `SemanticHandle`. В Core 2 runtime выводит ключ для каждого вызова, сохраняет его во всех попытках и повторных отправках и передаёт адаптеру. Чтобы повторить эффект после `Unknown`, решатель указывает *намерение* (intent) прежнего вызова ([Core §3.2](../../spec/ballarch-core-2.0.md#32-call-lifecycle)).
5. **Триггеров применимости нет.** Core применяется к состоянию, которое вызывает порты Idempotent или NonIdempotent; всё остальное — обычный код ([Core §1](../../spec/ballarch-core-2.0.md#1-scope)). Объявлять отсутствие чего-либо не нужно.
6. **Правил меньше, и у каждого есть названная проверка.** В Core 2 16 правил, R1–R16 ([Core §5](../../spec/ballarch-core-2.0.md#5-kernel-rules)). Материал о безопасности и проектировании протоколов стал рекомендациями (§8).

## Что вернулось из 1.5

Несколько идей 1.5 вернулись в Core 2 в более компактной форме.

| 1.5 | Core 2.0 |
|---|---|
| PBA-30: честные чтения, `ReadResult` с `ConsistencyStamp` | R12: чтение возвращает последнее зафиксированное состояние с его ревизией и ничего не фиксирует. В эталоне на Kotlin `Runtime.read` возвращает `Snapshot` (идентификатор, ревизия, состояние), а типизированный `watch` выдаёт по одному снимку на каждую фиксацию. |
| PBA-40: никакого обязательного переключения потока | §3.1: runtime может выполнить шаг в том потоке, который передал вход. Выполнение на месте (inline) — выбор планировщика, а не профиль. В эталоне на Kotlin есть `InlineScheduler`. |
| Дерево решений о границах и раздел «Что не является Ball» (1.5 §4.4, §4.6) | [Руководство по выбору](decision-guide.md), согласованное с тем, где применяется Core (§1). |
| PBA-12: эпоха владения или отсечение (fence) в хранилище для перемещаемого владельца | R16: хранилище runtime в профиле Durable не допускает второй runtime или отвергает записи от всех runtime, кроме последнего. `MemoryStore` применяет отсечение (fencing), а `FileStore` берёт блокировку операционной системы. |
| PBA-14: виды состояния | Рекомендации в [руководстве по структуре](structure.md): бизнес-состояние — в Ball, состояние представления — производное, состояние ввода — в UI-фреймворке. |
| PBA-17: устаревшие результаты по дескриптору | `CallRef` в состоянии указывает вызов, завершение которого может изменить то, что показано (§8.3). |
| PBA-21: срок хранения, покрывающий горизонт повторов | Окно дедупликации привязки, учитываемое в предварительной проверке (preflight, §3.5). |

## Что стало с каждым законом

*Сохранён* — обязательство остаётся нормативным, возможно, в другой формулировке. *По построению* — API ядра или runtime делает нарушение невозможным или сообщает о нём, поэтому правило для автора не нужно. *Рекомендация* — текст перенесён в ненормативный §8 или в руководство. *Исключён* — Core 2 больше не делает этого утверждения; причина указана.

## Навыки для агентов

Навыки 1.5 — `pokeball`, `pokeball-async`, `pokeball-binding`, `pokeball-composition` и `pokeball-review` — не перенесены: они применяют законы (от PBA-01 до PBA-44) и словарь 1.5. Удалите их из своего агента и установите единственный навык Core 2 из [`skills/ballarch/`](../../skills/ballarch/SKILL.md).

## Перенос фичи

1. Оставьте прежнюю логику Nucleus телом `decide`. Замените ветвление по видам Pulse одним `when` по типу запроса, а для завершений и уведомлений используйте `complete` и `observe`.
2. Замените каждый `EffectRequest` вызовом на `AdapterPort` через `ctx.call` и сохраните его `CallRef` в состоянии. Честно выберите класс эффекта порта в корне композиции. Перенесите транспортный код в `Adapter`, который передаёт получателю `Invocation.idempotencyKey`, и проверьте его набором проверок соответствия адаптера.
3. Замените `OperationId`, который защищает повторяемый эффект, намерением из `ctx.newIntent()`: храните его в состоянии и указывайте в каждом вызове, который запрашивает этот эффект. Объявите окно дедупликации получателя в привязке.
4. Замените `ModuleCommandRequest` вызовом на `BallPort` цели. Замените `SignalPublication` на `Publish` и подписку в корне композиции.
5. Удалите код дескрипторов, материализаторов статуса и объявлений об отсутствии триггеров. Храните статус в состоянии, а экраны и эндпоинты пусть получают его через `Runtime.read` или `watch`.
6. Обрабатывайте единственное завершение каждого вызова в `complete` с помощью `outcomeFor`: `Done`, `NotDone` и, для портов с эффектом, `Unknown`. После `Unknown` повторите вызов на порте Idempotent с тем же намерением или объявите сверку в привязке (§8.4). Никогда не повторяйте эффект NonIdempotent вслепую (R15).
