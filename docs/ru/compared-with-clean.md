# Ballarch в сравнении с Clean Architecture

Clean Architecture ограничивает зависимости: «зависимости в исходном коде могут указывать только внутрь» ([Martin 2012](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html), дата обращения: 2026-10-27). Ballarch ограничивает утверждения об эффектах: что код вправе сказать о случившемся после того, как вызвал что-то, способное завершиться ошибкой или сработать дважды. Эти вопросы независимы, поэтому подходы сочетаются. В Ballarch адаптеры остаются на краю системы, корень композиции — один, а команда может сохранить свои слои вокруг Ball.

Это руководство разбирает одну фичу в обоих стилях. Измеренного сравнения в нём нет. Строки о сбоях — иллюстрация, а [спецификация](../../spec/ballarch-core-2.0.md#10-trade-offs-and-known-limitations) ничего не утверждает о продуктивности, объёме кода или числе дефектов.

## Фича

Android-приложение оформляет заказ. Пользователь собирает корзину и нажимает «Оформить заказ». Приложение вызывает `POST /orders` на сервере, который принимает заголовок `Idempotency-Key` и в течение 24 часов дедуплицирует запросы по ключу. Ещё сервер предоставляет `GET /orders?key=…`: этот запрос возвращает заказ, оформленный с этим ключом, если такой есть.

Реальные API хранят ключи ограниченное время. По состоянию на 2026-10-27 Stripe API v1 может удалить ключ, которому не меньше 24 часов, а запрос с удалённым ключом обрабатывается как новый ([Stripe, idempotent requests](https://docs.stripe.com/api/idempotent_requests), дата обращения: 2026-10-27).

Руководство Google называет доменный слой необязательным и предупреждает: если навязывать use case каждому вызову, это «может добавить сложности при малой пользе» ([domain layer](https://developer.android.com/topic/architecture/domain-layer), дата обращения: 2026-10-27). Без доменного слоя из левой колонки уходят use case и интерфейс репозитория.

В колонке Ballarch нет ни репозитория, ни use case, потому что этой фиче они не нужны. Команда, которая хочет их сохранить, может оставить их обычным кодом: Ball они не становятся. Таблица показывает типичную раскладку, а не меру трудозатрат, и колонка Ballarch вдобавок зависит от runtime.

`PlaceOrder.kt`, `PlaceOrderApp.kt` и `PlaceOrderTest.kt` есть в репозитории, в [`examples/place-order`](../../reference/kotlin/examples/place-order/). Пример написан на обычном Kotlin/JVM: экрана, HTTP-адаптеров и хранилища для Android в репозитории нет.

## Когда что-то идёт не так

Колонка Clean описывает прямолинейную реализацию. ViewModel вызывает use case в `viewModelScope`, репозиторий отправляет один `POST`, а любое исключение превращается в состояние ошибки с кнопкой «Повторить». Если ключ идемпотентности вообще отправляется, он создаётся заново для каждого запроса. Строки показывают, что происходит, когда для такого случая никто не дописал код. **Это иллюстрация, а не измерение.**

| Ситуация | Прямолинейный Clean (иллюстрация) | Ballarch, пример `place-order` | Чем проверено |
|---|---|---|---|
| Сервер создал заказ, а его ответ потерялся | Тайм-аут превращается в «Не удалось оформить заказ». «Повторить» отправляет новый запрос, и сервер создаёт второй заказ. | Если попытка закончилась без ответа, runtime повторяет запрос с тем же ключом, и сервер возвращает первый заказ. Если потерялись все ответы, runtime после истечения 30-секундного горизонта доставки читает `GET /orders?key=…` и так завершает вызов. Если не удалось и это чтение, стадия — `Checking`, а «Повторить» повторяет заказ с тем же намерением (intent) и ключом. | `under every fault and crash point no order is placed twice, and no Unknown is shown as NotPlaced`; `trying again after Unknown repeats the order with the same key, which the server does not place twice` |
| Двойное нажатие | Две корутины отправляют два запроса, и сервер создаёт два заказа. | Второй `Place` застаёт `Placing` с той же корзиной и присоединяется к нему. Ничего не отправляется. Другая корзина отклоняется. | `decide places a new order, joins a double tap, and repeats an unknown one with its intent` |
| Процесс умирает во время запроса | Нигде не записано, что запрос ушёл. Пользователь отправляет заказ снова, и новый запрос может создать второй заказ. | В профиле Durable вызов и его фаза сохраняются до того, как запрос уходит. После перезапуска runtime отправляет вызов, который так и не ушёл, а вызов, который мог уйти, отправляет повторно с исходным ключом или сверяет ([Core §3.7](../../spec/ballarch-core-2.0.md#37-crash-and-recovery)). | перебор из первой строки, с падением перед любой из первых 16 задач планировщика |
| Пользователь уходит с экрана | «Любая корутина, запущенная в этой области, автоматически отменяется, когда `ViewModel` очищается» ([coroutines](https://developer.android.com/topic/libraries/architecture/coroutines), дата обращения: 2026-10-27). Запрос мог уже уйти в сеть, и приложение так и не узнаёт, существует ли заказ. | Runtime живёт на уровне приложения, поэтому уход с экрана не затрагивает вызов. Когда экран открывается снова, он читает стадию. | по построению: Ball не живёт в экране |
| «Повторить» через неделю после неизвестного результата | Новый запрос создаёт второй заказ. Сохранённый ключ не помог бы: сервер его уже забыл. | Привязка объявляет окно дедупликации в 24 часа минус горизонт. Предварительная проверка (preflight) отклоняет вызов: он закончился бы за пределами окна, отсчитанного от выдачи его намерения. Ничего не отправляется, стадия остаётся `Checking`. Заказ по-прежнему не завершён: приложение должно найти его по ключу или передать в поддержку. | `a week later the deduplication window refuses to try again, and nothing is sent` |
| Сервер отклоняет корзину с кодом 422 | Показывается состояние ошибки. Это правильно: ничего не создано. | Адаптер, который переводит 422 в `NotApplied`, как HTTP-адаптер примера shop, завершает вызов `NotDone` с первой попытки, и стадия становится `NotPlaced` с причиной. Результат тот же. Единственное отличие: после `Unknown` исход `NotDone` говорит только о повторе, поэтому стадия возвращается к `Checking`. | `complete shows NotPlaced only when no earlier call of the order may have placed it` |

Последнее правило видно в `complete`. `when` здесь — выражение над sealed-типом `Outcome`, поэтому без ветки `Unknown` код не компилируется.

Из [`reference/kotlin/examples/place-order/src/main/kotlin/ballarch/examples/placeorder/PlaceOrder.kt`](../../reference/kotlin/examples/place-order/src/main/kotlin/ballarch/examples/placeorder/PlaceOrder.kt):

```kotlin
    override fun complete(state: PlaceOrderState, completion: Completion<*>, ctx: Context): Step<PlaceOrderState, PlaceOrderState> {
        if (state !is Placing) return step(state)
        return when (val outcome = completion.outcomeFor(state.call)) {
            is Outcome.Done -> step(Placed(outcome.value.id))
            // After an Unknown, NotDone is about this call only: the earlier one may have placed the order.
            is Outcome.NotDone -> step(if (state.repeat) Checking(state.cart, state.intent) else NotPlaced("${outcome.reason}"))
            is Outcome.Unknown -> step(Checking(state.cart, state.intent))
            null -> step(state) // a completion of another call
        }
    }
```

## Справедливости ради

Аккуратная реализация на Clean может закрыть каждую строку таблицы:

- ViewModel может игнорировать второе нажатие, пока запрос в пути;
- репозиторий может создавать один ключ на заказ, хранить его вместе с черновиком и использовать повторно;
- запрос может выполняться в области, которая живёт дольше экрана. Так советует руководство Google по слою данных, а для «бизнес-операций», которые «должны пережить смерть процесса», оно советует WorkManager ([data layer](https://developer.android.com/topic/architecture/data-layer), дата обращения: 2026-10-27);
- состояние UI может получить вариант «неизвестно», а поиск по ключу — его разрешить;
- репозиторий может отказываться повторно использовать ключ, который старше срока его хранения на сервере.

Разница в том, где живёт этот код. В Clean каждая фича пишет своё хранилище ключей, защиту от двойной отправки, восстановление и сверку или вызывает общий хелпер, написанный командой; архитектура не требует этого хелпера и не проверяет его. В Ballarch всё это написано один раз, в runtime, который проверяют тесты соответствия:

- runtime классифицирует каждый исход по классу эффекта, который объявляет порт, и выводит ключи из намерений ([Core §3.2](../../spec/ballarch-core-2.0.md#32-call-lifecycle));
- композиция отклоняет политику повторов на NonIdempotent-порте, а предварительная проверка отклоняет дедлайн за пределами объявленного окна ([Core §3.5](../../spec/ballarch-core-2.0.md#35-bounds-and-preflight));
- `Unknown` — вариант `Outcome`, поэтому компилятор требует для него ветку.

Чего Ballarch не делает: он не решает, что показать на экране. Автор по-прежнему пишет стадию `Checking` и правило для «Повторить». Сверка объявляется в привязке, но работает, только если сервер умеет искать заказ по ключу и соблюдает горизонт доставки ([Core §10](../../spec/ballarch-core-2.0.md#10-trade-offs-and-known-limitations)).

Аккуратный Clean так же корректен, как Ballarch, если такую заботу получает каждая фича. Ballarch — ставка на то, что эту заботу не нужно повторять в каждой фиче. Окупается ли эта ставка в команде, не измерялось.

## Чего стоит Ballarch

- **Зависимость от runtime.** Ядро и runtime на уровне приложения, с планировщиком. Inline-планировщик может выполнять в главном потоке шаги Ball интерфейса в профиле Transient. Место Ball в профиле Durable — в фоновом цикле: так запись в хранилище не попадает в главный поток.
- **По sealed-стадии на каждый шаг.** В том числе стадия «пока никто не знает», которую интерфейс должен показать ([честный интерфейс](honest-ui.md)).
- **Сериализуемое состояние в профиле Durable.** Стадии, намерения и ссылки на вызовы сохраняются. Изменение формы состояния требует версии состояния и миграции ([Core §6.1](../../spec/ballarch-core-2.0.md#61-evolution)).
- **Хранилище.** Оно должно соответствовать контракту хранилища ([Core §6](../../spec/ballarch-core-2.0.md#6-profiles)). Один вызов с эффектом, получивший ответ `Done`, стоит трёх долговечных записей (это проверяет `RuntimeTest`). В эталонной реализации есть хранилище в памяти и файловое хранилище, а хранилища на Room или SQLite нет; одно такое описано в [привязках](bindings.md).
- **Пять понятий.** Ball с решателем, порт с классом эффекта, три исхода, намерение и привязка в корне композиции.
- **Объявления, которые ничто не проверяет.** Класс эффекта, окно дедупликации и горизонт доставки берутся из контракта сервера. Если они неверны, неверны и гарантии ([Core §10](../../spec/ballarch-core-2.0.md#10-trade-offs-and-known-limitations)).
- **Сервер, который помогает.** Без ключа идемпотентности порт — NonIdempotent, а без поиска по ключу каждый потерянный ответ заканчивается `Unknown` и доходит до пользователя.

## Внедрение в приложение на Clean

Ballarch регулирует только Ball ([Core §1](../../spec/ballarch-core-2.0.md#1-scope)). Переносить можно по одной фиче.

1. **Оставьте путь чтения.** Репозитории, кэши, пагинация, запросы Room и мапперы остаются как есть. Это не Ball.
2. **Перенесите путь записи.** Каждый use case, который отправляет запрос с эффектом, становится Ball. Метод репозитория, который отправлял запрос, становится адаптером: он сохраняет свой HTTP-вызов, передаёт ключ идемпотентности от runtime, переводит ответ в результат адаптера и никогда не повторяет запрос. Проверьте, что и HTTP-клиент внутри адаптера не повторяет запросы сам ([R8](../../spec/ballarch-core-2.0.md#52-runtime-rules)).
3. **Измените ViewModel.** Она отправляет запросы в runtime, а не вызывает use case. Стадию Ball она читает через `read` или `watch` и переводит её в состояние UI чистой функцией ([структура приложения](structure.md)).
4. **Добавьте привязку.** Объявите класс эффекта, окно и горизонт в корне композиции.

Код, который вызывает порт с эффектом вне Ball, не покрыт гарантиями Core, поэтому смешанное приложение ничего не утверждает о ещё не перенесённых частях.
