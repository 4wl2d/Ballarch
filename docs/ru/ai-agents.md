# Ballarch и ИИ-агенты

Это руководство описывает два применения. **Агент-программист** (coding agent) пишет или меняет код на Ballarch. В **агентной системе** языковая модель предлагает действия, а инструменты их выполняют; здесь такая система построена из Ball и портов. Никто не измерял, помогает ли Ballarch агентам того или другого вида. Это руководство такой пользы не заявляет ([Core §10](../../spec/ballarch-core-2.0.md#10-trade-offs-and-known-limitations)).

За наброском нет эталонного кода. Остальной код скопирован из исходного файла, названного над ним.

## 1. Агенты-программисты и читаемость кода

Фича на Ballarch держит в одном месте факты, которые нужны агенту:

- **Один файл на Ball.** Порты, стадии, `decide` и `complete` лежат рядом. См. [`PlaceOrder.kt`](../../reference/kotlin/examples/place-order/src/main/kotlin/ballarch/examples/placeorder/PlaceOrder.kt). Его привязка с повторами, окном и сверкой лежит в подпакете `app`: [`PlaceOrderApp.kt`](../../reference/kotlin/examples/place-order/src/main/kotlin/ballarch/examples/placeorder/app/PlaceOrderApp.kt).
- **Запечатанные стадии.** Каждая стадия операции — отдельный тип, включая ту, на которой результат ещё никому не известен (`Checking` в примере place-order).
- **Исчерпывающие исходы.** `complete` сопоставляет `Done`, `NotDone` и `Unknown` без ветки «всё остальное», поэтому компилятор сообщает о пропущенном случае.
- **`CallRef` в состоянии.** `completion.outcomeFor(ref)` возвращает `null` для любого другого вызова, поэтому запоздавшее или вытесненное завершение не может изменить не ту стадию.
- **Порог.** Код, который не вызывает ни Idempotent-, ни NonIdempotent-портов, — обычный код ([Core §1](../../spec/ballarch-core-2.0.md#1-scope)). Не нужно заготавливать use case, репозитории или модели для каждого слоя.

Такую раскладку мотивируют три исследования. Ни одно из них не проверяло Ballarch.

- Dente, Satriani и Papotti, [*Constraint Decay: The Fragility of LLM Agents in Backend Code Generation*](https://arxiv.org/abs/2605.06445), arXiv:2605.06445 (дата обращения: 2026-10-27). На многофайловых бэкенд-задачах доля пройденных агентами проверок (assertions) падала по мере добавления структурных ограничений: обязательной слоистости Clean Architecture, базы данных и ORM. В разборе по отдельным ограничениям (§5.1) слоистость снижала долю пройденных проверок, а сильнее всего её снижали ограничения на базу данных.
- Zhu, Tsantalis и Rigby, [*AI-Generated Smells: An Analysis of Code and Architecture in LLM and Agent-Driven Development*](https://arxiv.org/abs/2605.02741), arXiv:2605.02741 (дата обращения: 2026-10-27). Авторы сообщают, что более сильные модели порождают более раздутый и сильнее связанный код. В многофайловых репозиториях, которые для исследования сгенерировал агентный фреймворк, они описывают «модульный мираж» (modular mirage, §4.2.4): код разложен по файлам, но связанная логика разбросана между ними.
- Gloaguen и др., исследование файлов контекста уровня репозитория для агентов-программистов, [arXiv:2602.11988](https://arxiv.org/abs/2602.11988) (дата обращения: 2026-10-27). Файлы контекста в целом не повышали долю успешно решённых задач и увеличивали стоимость инференса.

Меняет ли раскладка Ballarch эти результаты, неизвестно. [Навык для агентов](../../skills/ballarch/SKILL.md) пока не оценивался.

## 2. Сенсоры

Böckeler в статье [*Harness engineering for coding agent users*](https://martinfowler.com/articles/harness-engineering.html) (дата обращения: 2026-10-27) разделяет направляющие (guides), которые настраивают агента до того, как он начнёт действовать, и сенсоры (sensors), которые проверяют его работу после. Ballarch предлагает такие сенсоры:

| Сенсор | Что ловит | Где есть |
|---|---|---|
| Чистота решателя | Ввод-вывод, часы, случайность, потоки или обращение к runtime в решателе (R2) | `deciderPurity` (ArchUnit) в эталоне на Kotlin; [`check_purity.sh`](../../reference/c/tools/check_purity.sh) для C. В Rust — крейт решателя, который зависит только от крейта ядра (эталона нет). |
| Отказы композиции | Политика повторов или тайм-аут попытки на NonIdempotent-порте; окно дедупликации на порте, который не является Idempotent; сверка на Safe-порте | `Composition.adapter` бросает исключение при построении композиции |
| Ошибки предварительной проверки (preflight) | Намерение на порте, который не является Idempotent-портом адаптера; дедлайн за пределами окна дедупликации | Runtime отвергает решение ([Core §3.5](../../spec/ballarch-core-2.0.md#35-bounds-and-preflight)) |
| Исчерпывающее сопоставление | Пропущенная ветка `Unknown` | `when` или `switch` по типу исхода без ветки по умолчанию |
| Проверка трасс | Нарушения T3 и T5–T9 в трассах соответствия | [`tools/oracles.py`](../../tools/TRACE-FORMAT.md#checking-a-trace), запускается в CI |
| Проверки адаптеров | Адаптер, который повторяет запросы, сообщает дважды, заявляет `NotApplied` без доказательства или придумывает ключи (C1–C5) | `AdapterConformance` в `ballarch-testkit` |
| Границы модулей | Фича, которая импортирует реализацию другой фичи | `featuresUseOnlyPublicApis`, `checkModuleBoundaries` |

Отказы композиции, из `reference/kotlin/ballarch-runtime/src/main/kotlin/ballarch/runtime/Composition.kt`:

```kotlin
        require(retry.maxAttempts == 1 || port.effect != EffectClass.NonIdempotent) {
            "port '${port.name}' is NonIdempotent and cannot be retried"
        }
        require(retry.attemptTimeoutMillis == null || port.effect != EffectClass.NonIdempotent) {
            "port '${port.name}' is NonIdempotent and cannot have an attempt timeout"
        }
```

Сенсор работает, только если агент не может его изменить. Zhong, Raghunathan и Carlini в [*ImpossibleBench*](https://arxiv.org/abs/2510.20270), arXiv:2510.20270 (дата обращения: 2026-10-27), измеряют, как часто агенты «проходят» задачи, которые решить невозможно, например меняя тесты. Держите оракулы, тесты соответствия, переборы и архитектурные правила вне области записи агента ([Core §8.7](../../spec/ballarch-core-2.0.md#8-guidance-non-normative)). Закрепите их версии или запускайте их в CI из основной ветки, а каждое их изменение рецензируйте как изменение спецификации.

## 3. Агентные системы: устройство

Прогон агента — это Flow: им владеет один Ball ([Core §7.2](../../spec/ballarch-core-2.0.md#72-workflows)). Его состояние содержит:

- **цель** — от пользователя, доверенная;
- **план** или последнее предложение модели — недоверенное;
- **журнал вызовов инструментов** (tool ledger): для каждого вызова инструмента — его `CallRef`, намерение и исход;
- **одобрения** — выданные и ожидающие.

**Модель — это порт адаптера.** Вызов, который только возвращает текст, ничего не меняет у получателя, поэтому объявите этот порт Safe. Тогда его можно повторять, и он никогда не заканчивается `Unknown`. Повтор стоит токенов, а не эффектов. Модель на стороне провайдера, которая сама запускает инструменты, — не Safe. Объявите её NonIdempotent или отключите её встроенные (hosted) инструменты и пропускайте каждый инструмент через порт.

**Потоковая выдача.** Ответ, полученный потоком (streaming), — всё равно одно завершение. Адаптер читает поток до конца и сообщает один раз. Поток, оборванный на середине, — это `Failed`, поэтому runtime повторяет Safe-вызов с начала в пределах бюджета попыток или завершает его `NotDone(NoAnswer)`. Вызовы инструментов, которые приходят дельтами, разбирайте только из полного ответа, чтобы частично полученный вызов инструмента никогда не выполнился. Адаптер может передавать токены в UI по мере поступления; это данные для отображения, а не состояние Ball, и они ничего не решают. Несколько вызовов инструментов в одном ответе становятся несколькими вызовами в одном решении, у каждого свой `CallRef` в журнале вызовов инструментов.

**Зафиксированный ответ не запрашивается повторно.** Ответ модели приходит как завершение и фиксируется вместе с решением, которое его обрабатывает. После падения Durable-runtime восстанавливает зафиксированное состояние и выходы. Он не перезапускает решатели, чтобы получить их заново (R4), поэтому модель не спрашивают снова об ответе, который у Ball уже есть. Вызов модели, который в момент падения был в пути, может быть отправлен снова, как и любой Safe-вызов ([Core §3.2](../../spec/ballarch-core-2.0.md#32-call-lifecycle)).

**Политика превращает предложения в вызовы.** Ответ модели — недоверенный вход ([Core §8.6](../../spec/ballarch-core-2.0.md#8-guidance-non-normative)). `complete` разбирает его в предложение. Детерминированный код в решателе проверяет инструмент, аргументы, бюджет и одобрения и только после этого делает вызов. Модель никогда не порождает вызов сама. Это следует подходу CaMeL (Debenedetti и др., [arXiv:2503.18813](https://arxiv.org/abs/2503.18813), дата обращения: 2026-10-27), в котором недоверенные данные не могут изменить поток управления программы, и паттернам Beurer-Kellner и др. ([arXiv:2506.08837](https://arxiv.org/abs/2506.08837), дата обращения: 2026-10-27). Сам по себе Ballarch не даёт их гарантий безопасности. Он даёт политике одно место: чистую функцию, которую можно протестировать.

Набросок: эталонного кода нет, соответствие не заявляется.

```kotlin
// in complete(), while the Ball waits for the model
is Asking -> when (val answer = completion.safeOutcomeFor(state.ask)) {
    is Outcome.Done -> next(state, Proposal.parse(answer.value), ctx)  // model text becomes data
    is Outcome.NotDone -> finish(state.withNote("model unavailable"))
    null -> step(state)                                                // another call's completion
}

fun next(state: Asking, p: Proposal?, ctx: Context): Step<AgentState, TaskReport> = when {
    p !is Proposal.UseTool -> finish(state)
    p.tool !in state.goal.allowedTools -> ask(state.refused(p), ctx)
    needsApproval(p.tool, state) -> requestApproval(state, p, ctx.newIntent(), ctx)
    else -> useTool(state, p, ctx.newIntent(), ctx)
}
```

## 4. Инструменты — это порты

Каждый инструмент — порт адаптера. Его класс эффекта объявляется в коде, которым владеет приложение. Собственное описание инструмента помогает выбрать класс, но никогда не заменяет это объявление ([Core §2.6](../../spec/ballarch-core-2.0.md#26-declaring-effect-classes)).

По состоянию на 2026-10-27 [спецификация MCP (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) требует, чтобы клиенты считали аннотации инструментов недоверенными, если они получены не от доверенных серверов. Её [схема](https://modelcontextprotocol.io/specification/2026-07-28/schema) называет каждую аннотацию подсказкой (hint). `idempotentHint` она определяет так: повторные вызовы с теми же аргументами не дают дополнительного эффекта.

| Что объявляет инструмент | Как объявить порт | Почему |
|---|---|---|
| Аннотации нет, или сервер недоверенный | NonIdempotent | Класс, который не установлен, — NonIdempotent (§2.6). |
| `readOnlyHint: true` от сервера, который вы проверили | Safe, объявленный в вашем коде | Подсказка информирует, решает ваше объявление. Чтение, которое что-то меняет у получателя, например помечает сообщение прочитанным, — не Safe. |
| `idempotentHint: true` и аргумент-ключ, по которому сервер дедуплицирует | Idempotent; адаптер заполняет этот аргумент значением `invocation.idempotencyKey` | Idempotent в Ballarch означает дедупликацию по ключу, который передаёт runtime ([Core §2](../../spec/ballarch-core-2.0.md#2-model)). |
| `idempotentHint: true` без такого аргумента | NonIdempotent | «Те же аргументы» не мешают запоздавшей попытке примениться после более позднего изменения. |

Адаптер инструмента сообщает о результате так же, как любой адаптер ([приложение D](../../spec/ballarch-core-2.0.md#appendix-d-adapter-checks-normative)):

- результат без `isError` → `Ok(value)`;
- `isError: true` → `Failed`, если только проверенный вами контракт сервера не говорит, что эта ошибка ничего не применила; тогда `Refused` (C3);
- задача, статус которой больше нельзя прочитать, а также тайм-аут или разорванное соединение после отправки запроса → `Failed`;
- в соединении отказано до того, как запрос был записан → `NotApplied`, с этим доказательством.

Runtime превращает `Failed` в повтор либо в `Unknown` на порте с эффектом и в `NotDone(NoAnswer)` на Safe-порте. Контракт адаптера, из `reference/kotlin/ballarch-runtime/src/main/kotlin/ballarch/runtime/Adapter.kt`:

```kotlin
 * Contract (checked by the adapter conformance kit in `ballarch-testkit`):
 * - report through [done] at most once per invocation; later reports are ignored;
 * - never retry internally; retries belong to the runtime (see [RetryPolicy]);
 * - report [AdapterResult.NotApplied] only with evidence that the request had
 *   no effect; when in doubt report [AdapterResult.Failed], which the runtime
 *   classifies by the port's effect class;
 * - pass [Invocation.idempotencyKey] to a destination that accepts one, and
 *   never create a key of its own: only the runtime creates keys.
```

## 5. Одобрения

Одобрение — это вызов через порт одобрения, например к сервису, который спрашивает человека и записывает ответ.

1. Политика решает, что вызов инструмента требует одобрения. Она выпускает намерение для вызова инструмента через `ctx.newIntent()` и вызывает порт одобрения. Запрос называет предлагаемый вызов инструмента и несёт идентификатор этого намерения.
2. Объявляйте порт одобрения Idempotent, только если сервис одобрений дедуплицирует по ключу идемпотентности. Дайте вызову одобрения собственное намерение и называйте его снова, когда спрашиваете повторно после `Unknown`: тогда человек увидит один запрос на одобрение, а не два. Не называйте в вызове одобрения намерение вызова инструмента: вызовы, которые называют одно намерение, должны запрашивать один и тот же эффект ([Core §3.2](../../spec/ballarch-core-2.0.md#32-call-lifecycle)).
3. Вызов инструмента делает только решение, которое фиксирует `Done(Approved)`. Runtime отправляет вызов только после фиксации его решения (R5), поэтому одобрение записано до того, как инструмент запустится. Отказ — это записанный ответ: вызов инструмента так и не делается. Окно дедупликации отсчитывается от выпуска намерения ([Core §3.5](../../spec/ballarch-core-2.0.md#35-bounds-and-preflight)), поэтому долгое ожидание одобрения его расходует.

Вызов должен завершиться к своему дедлайну, а эталон по умолчанию ограничивает тайм-ауты вызовов десятью минутами (`Limits.maxTimeoutMillis`). Если человеку может понадобиться больше времени, пусть вызов одобрения только регистрирует запрос и отвечает `Done(Requested)`. Затем сервис одобрений присылает ответ человека как запрос на порт агентного Ball, аутентифицированный его входящим адаптером, а `decide` принимает такой запрос только для ожидающего одобрения. Вызов инструмента по-прежнему делает только решение, которое фиксирует одобрение.

Когда нужно одобрение:

| Порт инструмента | Одобрение |
|---|---|
| Safe | Ради эффектов — не нужно. Политика всё же может спросить перед чтением личных данных. |
| Idempotent | Одно на намерение. Повтор с тем же намерением после `Unknown` не спрашивает снова: получатель применит его не более одного раза. |
| NonIdempotent | На каждый вызов. Каждый вызов может сработать, поэтому одно одобрение никогда не покрывает другой вызов. |

По состоянию на 2026-10-27 в документации [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/human_in_the_loop/) сказано, что одобрение разрешает вызов инструмента, но не гарантирует, что он выполнится ровно один раз. Здесь то же самое. «Не более одного раза» обеспечивают класс эффекта и R8, а не одобрение.

## 6. Ключи выдаёт только runtime

- **Один ключ на вызов.** Runtime выводит ключ идемпотентности для каждого вызова, один и тот же для всех попыток. Вызовы, которые называют одно намерение, делят этот ключ ([Core §3.2](../../spec/ballarch-core-2.0.md#32-call-lifecycle)). Адаптер передаёт `invocation.idempotencyKey` (C5). Ни модель, ни решатель ключей не создают ([R8](../../spec/ballarch-core-2.0.md#52-runtime-rules)). Если модель вписала ключ в аргументы инструмента, адаптер его заменяет.
- **Без скрытых повторов.** Адаптер не должен повторять запросы (R8, C2). Отключите повторы в SDK и HTTP-клиентах, которыми пользуются адаптеры. Вместо этого задайте в привязке `RetryPolicy` с тайм-аутом попытки; на NonIdempotent-порте композиция такую политику отвергнет.
- **Без слепого повторения.** После того как вызов NonIdempotent-инструмента закончился `Unknown`, Ball не должен снова запрашивать тот же эффект, пока не получит доказательство, что первый вызов эффекта не имел ([R15](../../spec/ballarch-core-2.0.md#51-author-rules)). Таким доказательством служит Safe-чтение статуса, сделанное после горизонта доставки получателя и сообщающее, что эффект не применён. На порте со сверкой runtime делает это чтение сам, и чтение, сообщающее о неприменении, завершает вызов `NotDone`, а не `Unknown`. После `Unknown` на Idempotent-инструменте повторяйте вызов, называя намерение предыдущего вызова.
- **Окно.** Объявите `dedupWindowMillis` для сервера инструментов, который забывает ключи. Тогда runtime отвергнет вызов, дедлайн которого наступает после конца окна, отсчитанного от намерения вызова (сценарий S9). Когда окно прошло, вместо повтора выполняйте сверку.

## 7. Итоговый отчёт

Отчёт сообщает, что сделали инструменты. Решатель вычисляет его из журнала вызовов инструментов, а не из слов модели. В работе Li [*Where Does Exactly-Once Live?*](https://arxiv.org/abs/2609.29095), arXiv:2609.29095 (дата обращения: 2026-10-27), показано, что в эпизодах, где агенты продублировали эффект, они обычно сообщали об успехе.

Набросок: эталонного кода нет, соответствие не заявляется.

```kotlin
data class TaskReport(
    val status: Knowledge,            // from the tool ledger by the algebra, never from the model
    val uncertain: List<CallRef<*>>,  // tool calls that ended Unknown and were not settled since
    val narrative: String,            // the model's words, shown as such
)

val status = ledger.entries.fold(Knowledge.NoEffects) { k, e -> k + e.knowledge }
```

- `status` учитывает каждый вызов инструмента по таблице R14 ([Core §5.1](../../spec/ballarch-core-2.0.md#51-author-rules)). Вызов, который Ball ещё может сделать, считается как `Maybe`, как и открытый вызов.
- `uncertain` перечисляет вызовы, которые, возможно, придётся проверить человеку.
- `narrative` объясняет, но никогда не задаёт `status`.

Отправляйте отчёт, когда прогон завершён: нет ни одного открытого вызова инструмента и ни одного, который ещё предстоит сделать ([Core §7.4](../../spec/ballarch-core-2.0.md#74-composition-closure)). Примите запрос через `acceptLater` и ответьте, когда прогон завершится. Сообщение о ходе работы до этого момента — снимок: помечайте его стадией и никогда не выдавайте за результат (R14). Так отвечает пример с поездкой, из `reference/kotlin/examples/trip/src/main/kotlin/ballarch/examples/trip/TripFlow.kt`:

```kotlin
    /** Ends the trip: nothing can change any more, so its knowledge is final and every waiting Book gets it. */
    private fun settle(state: TripState): Step<TripState, TripReply> {
        val settled = state.copy(stage = Stage.Settled, call = null, attempts = 0, awaiting = emptyList())
        val answer = status(settled)
        return Step(settled, state.awaiting.map { Reply(it, answer) })
    }

    private fun status(state: TripState) = TripReply.Status(state.stage, state.knowledge)
```

[Честный интерфейс](honest-ui.md) сопоставляет каждому значению знания сообщение и следующее действие.

## 8. Необязательная проверка: смертельная триада

Willison в статье [*The lethal trifecta for AI agents*](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) (дата обращения: 2026-10-27) предостерегает от агента, у которого одновременно есть три вещи: доступ к личным данным, контакт с недоверенным содержимым и способ связаться с внешним миром. Встроенной проверки на это в Ballarch нет. Но каждый инструмент — это порт, привязанный в одном корне композиции, поэтому такую проверку может сделать тест.

Набросок: эталонного кода нет, соответствие не заявляется.

```kotlin
enum class Exposure { PrivateData, UntrustedContent, SendsOut }

val exposures = mapOf(
    Inbox to setOf(Exposure.PrivateData, Exposure.UntrustedContent),
    WebFetch to setOf(Exposure.UntrustedContent, Exposure.SendsOut),  // a URL can carry data out
)

@Test fun `no agent holds all three`() {
    for ((agent, ports) in agentPorts) {  // listed by hand next to the composition root
        val held = ports.flatMap { exposures[it].orEmpty() }.toSet()
        assertTrue(held.size < Exposure.entries.size, "$agent holds the lethal trifecta")
    }
}
```

## Чего это стоит и чего это не делает

- Каждый прогон агента — это Ball с явными сериализуемыми стадиями. В профиле Durable каждый вызов инструмента с эффектом требует как минимум трёх долговечных записей ([Core §10](../../spec/ballarch-core-2.0.md#10-trade-offs-and-known-limitations)).
- Ballarch не останавливает промпт-инъекции и не решает, что может делать инструмент. Он ограничивает то, что может быть повторено, и то, что может утверждать отчёт.
- Ни один профиль не даёт выполнения внешних эффектов ровно один раз (R13).
