# Какие проблемы Ballarch решает, а какие нет

Пятнадцать повторяющихся проблем — от приложений до драйверов. Для каждой указано, где она встречается, какой механизм и какое правило Ballarch её решают, какие доказательства есть в этом репозитории и насколько это ново по оценке [Core §12](../../spec/ballarch-core-2.0.md#12-lineage-and-what-is-new-informative). Большинство механизмов — устоявшаяся практика.

Дата обращения ко всем веб-источникам — 2026-10-27, сведения о продуктах приведены по состоянию на эту дату. Каждый результат об эталонных реализациях проверяется тестом, который назван рядом с ним.

## Решаемые проблемы

### P1. Неопределённый исход выдаётся за обычную ошибку

- **Где встречается** (дата обращения: 2026-10-27): в Elm у `Http.Error` есть `Timeout` и `NetworkError`, и ни один из них не говорит, обработал ли сервер запрос ([elm/http](https://github.com/elm/http/blob/master/src/Http.elm)). Мутации Riverpod заканчиваются либо ошибкой, либо успехом ([Riverpod](https://riverpod.dev/docs/concepts2/mutations)). Результат инструмента MCP несёт булев флаг `isError` ([MCP](https://modelcontextprotocol.io/specification/2025-03-26/server/tools)). Stripe, напротив, советует считать ответ 500 «неопределённым» ([Stripe](https://docs.stripe.com/error-low-level)).
- **Механизм:** каждый вызов заканчивается исходом `Done`, `NotDone` или `Unknown`. Исход выбирает runtime по фазе вызова и записанному классу эффекта. Для `NotDone` нужно доказательство. С `CallRef` и `outcomeFor` ветка `Unknown` входит в тип решателя. Экран никогда не показывает `Unknown` как неудачу ([честный интерфейс](honest-ui.md)).
- **Правило:** R7, R15 ([Core §3.2](../../spec/ballarch-core-2.0.md#32-call-lifecycle)).
- **Доказательства здесь:** свойство трассы T7 сверяет каждый перебранный прогон с тем, что произошло на самом деле. `PlaceOrderTest`: `under every fault and crash point no order is placed twice, and no Unknown is shown as NotPlaced`.
- **Новизна:** третий исход известен давно («maybe» в RPC, `:info` в Jepsen). Одно правило runtime для всех портов, результат которого приходит в виде типизированного завершения, — новое сочетание (§12, строка 2).

### P2. Повторы включены по умолчанию и не учитывают, безопасен ли повтор

- **Где встречается** (дата обращения: 2026-10-27): политика повторов активностей в Temporal по умолчанию не ограничивает число попыток ([Temporal](https://docs.temporal.io/encyclopedia/retry-policies)). Юань и соавторы (Yuan et al.) показали, что простые тесты кода обработки ошибок предотвратили бы большинство изученных ими катастрофических сбоев ([OSDI 2014](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/yuan)).
- **Механизм:** каждый порт объявляет класс эффекта. Повторяет только runtime и только для портов Safe и Idempotent — в конечном бюджете попыток и с необязательным тайм-аутом попытки. Композиция отвергает повторы на порте NonIdempotent. Адаптеры никогда не повторяют.
- **Правило:** R8 ([Core §5.2](../../spec/ballarch-core-2.0.md#52-runtime-rules)).
- **Доказательства здесь:** `RuntimeTest`: `non-idempotent ports cannot be configured with retries`. Свойство трассы T8, свойство P4 в Alloy и внесённые ошибки повторной отправки в C (`BA_MUTANT_RESEND_AFTER_CRASH`) и RTL (`MUTANT_RETRY_FIRE`). Проверка адаптера C2 ловит вариант «broken: retries internally» в `HttpAdapterConformanceTest`.
- **Новизна:** как аннотация — не ново (методы HTTP, `idempotency_level` в protobuf, подсказки MCP). Запрет повторов при композиции и вывод исходов из класса входят в сочетание из строки 2. Общего бюджета повторов на несколько вызовов нет ([Core §8](../../spec/ballarch-core-2.0.md#8-guidance-non-normative), 8.4).

### P3. Окно падения между эффектом и его записью и ключи, сделанные вручную

- **Где встречается** (дата обращения: 2026-10-27): Inngest: «Запрос может выполниться успешно до того, как Inngest запишет результат шага» ([Inngest](https://www.inngest.com/docs/guides/handling-idempotency)). Stripe хранит ключи не меньше 24 часов и затем может их удалить, так что повторно использованный ключ может выполнить новый запрос ([Stripe](https://docs.stripe.com/api/idempotent_requests)). NServiceBus просит, чтобы срок хранения outbox превышал самый долгий повтор ([NServiceBus](https://docs.particular.net/nservicebus/outbox/)).
- **Механизм:** runtime сохраняет запись перед первой отправкой (write-ahead). Он выводит один ключ идемпотентности на вызов. Ключ сохраняется во всех попытках и повторных отправках и не повторяется после перезапуска в профиле Transient. Намерение (intent) даёт повтору после `Unknown` ключ прежнего вызова. Предварительная проверка (preflight) отвергает вызов, дедлайн которого переживает объявленное окно дедупликации получателя.
- **Правило:** R5, R8, ключи и намерения ([§3.2](../../spec/ballarch-core-2.0.md#32-call-lifecycle)), окна ([§3.5](../../spec/ballarch-core-2.0.md#35-bounds-and-preflight)), проверка адаптера C5 ([приложение D](../../spec/ballarch-core-2.0.md#appendix-d-adapter-checks-normative)).
- **Доказательства здесь:** сценарии S4b, S8 и S9 в `ExplorationTest` с негативными контролями. Адаптер, который создаёт собственный ключ на каждую попытку («a key of its own per attempt»), не проходит C5. `RuntimeRulesTest`: `a call is durably recorded as possibly sent before its adapter runs`.
- **Новизна:** запись перед отправкой не нова. Ключи, которые выводит runtime, намерения, окно, учитываемое в предварительной проверке, и необязательная сверка — скромное новое сочетание (строка 3).

### P4. Незавершённая работа привязана к экрану или задаче

- **Где встречается** (дата обращения: 2026-10-27): RIBs: «Все операции, которые выполняет Interactor, должны ограничиваться его жизненным циклом» ([RIBs](https://github.com/uber/RIBs/wiki)). Изменения в `SavedStateHandle` на Android «могут быть потеряны», если процесс завершён в фоне ([Android](https://developer.android.com/topic/libraries/architecture/viewmodel/viewmodel-savedstate)). В асинхронном Rust «future при уничтожении (drop) отменяется» ([Oxide RFD 400](https://rfd.shared.oxide.computer/rfd/400)).
- **Механизм:** обязательства принадлежат Ball, а не экрану, и runtime живёт столько же, сколько приложение. Интерфейс читает состояние через `read` и `watch`, которые ничего не фиксируют. В профиле Durable журнал вызовов переживает падение, и восстановление обрабатывает каждый вызов по его записанному классу ([структура](structure.md)).
- **Правило:** R6, R12, восстановление ([§3.7](../../spec/ballarch-core-2.0.md#37-crash-and-recovery)).
- **Доказательства здесь:** `FileStoreTest`: `a possibly sent non-idempotent call ends Unknown after a restart from disk and is not sent again`. `ShopAppTest`: `a screen reads the checkout status, which commits nothing`.
- **Новизна:** не ново — долговечные сущности и акторы. Мобильного хранилища в репозитории нет; `FileStore` проверен на принудительно завершённых процессах, а не на отключении питания.

### P5. В драйверах отмену, тайм-аут или сброс принимают за доказательство, что ничего не произошло

- **Где встречается** (дата обращения: 2026-10-27): errata Microchip к SAMA7G5: отмена в MCAN может сообщить об успехе, хотя «передача продолжается, пока не будет отправлен весь кадр» ([Microchip](https://onlinedocs.microchip.com/oxy/GUID-CFE060D6-6076-46C0-B8FD-60B6DA382A42-en-US-8/GUID-C02B5019-9536-43EE-BCA4-AA8D209A1A80.html)). В ветке рассылки linux-nvme 2018 года цитируется код драйвера, который по тайм-ауту опрашивает очередь завершений: «Did we miss an interrupt?» ([linux-nvme](https://lists.infradead.org/pipermail/linux-nvme/2018-May/017516.html)).
- **Механизм:** горизонт отправки — определённый момент, например рукопожатие `valid && ready`. После него для `NotDone` нужно доказательство, которое покрывает все попытки; подтверждение отмены таким доказательством не является. Адаптер сохраняет доказательства до сброса и опрашивает источник завершений, прежде чем сообщить `Failed`.
- **Правило:** R7, горизонты ([§2.5](../../spec/ballarch-core-2.0.md#25-boundaries-in-time)), C6.
- **Доказательства здесь:** тестбенч RTL ловит `MUTANT_WITHDRAWN_RETRY_NOT_DONE`; перебор прошивки ловит `BA_MUTANT_NACK_ALWAYS_CONCLUSIVE`. C6 проверяется только ревью.
- **Новизна:** приёмы драйверов давно устоялись. Одно правило исходов для сервисов, прошивки и RTL — узкое сочетание (строка 4). См. [уровни](levels.md).

### P6. Слои требуют лишних церемоний

- **Где встречается** (дата обращения: 2026-10-27): руководство Google по Android называет доменный слой необязательным и предупреждает, что навязанные use case «могут добавить сложности при небольшой пользе» ([Android](https://developer.android.com/topic/architecture/domain-layer)).
- **Механизм:** Core применяется только к состоянию, которое вызывает порты Idempotent или NonIdempotent. Отрисовка, кэши, Safe-чтения, мапперы и CRUD в одной транзакции остаются обычным кодом. Фича — один пакет; ни use case, ни репозиторий не обязательны.
- **Правило:** где применяется Core ([§1](../../spec/ballarch-core-2.0.md#1-scope)); структура модулей ([§7.1](../../spec/ballarch-core-2.0.md#71-module-structure)).
- **Доказательства здесь:** [пример place-order](../../reference/kotlin/examples/place-order/) — это один файл Ball, его привязка и его тест. Ни размер кода, ни трудозатраты здесь не измеряются.
- **Новизна:** польза для внедрения, а не исследовательский результат. См. [сравнение с Clean](compared-with-clean.md) и [руководство по выбору](decision-guide.md).

### P7. Агенты-программисты работают хуже, когда накапливаются ограничения и правила в виде текста

- **Где встречается** (дата обращения: 2026-10-27): качество работы агентов падает по мере того, как накапливаются структурные требования ([arXiv:2605.06445](https://arxiv.org/abs/2605.06445)). Файлы контекста репозитория в целом не повышают успешность решения задач, зато увеличивают стоимость инференса ([arXiv:2602.11988](https://arxiv.org/abs/2602.11988)). Агент с доступом к модульным тестам может удалить падающие тесты вместо того, чтобы исправить ошибку ([arXiv:2510.20270](https://arxiv.org/abs/2510.20270)).
- **Механизм:** важные правила выражены проверками, а не текстом: чистота решателя, отказы композиции, исчерпывающий разбор исходов и оракулы трасс. Оракулы находятся вне области, в которую пишут автоматические изменения.
- **Правило:** R2, R10, рекомендации по тестированию (§8.7).
- **Доказательства здесь:** `BallarchRulesTest` прогоняет каждое архитектурное правило на внесённых нарушениях. Оценки агентов, которые используют Ballarch, здесь нет, и [навык для агентов](../../skills/ballarch/SKILL.md) пока не оценивался.
- **Новизна:** не ново — архитектурные тесты и проверки вокруг агентов. Польза не заявляется. См. [агенты](ai-agents.md).

### P8. Агенты преувеличивают успех, а метаданные инструментов — лишь подсказка

- **Где встречается** (дата обращения: 2026-10-27): в большинстве эпизодов, где агенты продублировали эффект, они всё равно сообщили об успехе ([arXiv:2609.29095](https://arxiv.org/abs/2609.29095)). Клиенты MCP «ДОЛЖНЫ считать аннотации инструментов недоверенными», если сервер не доверенный ([MCP](https://modelcontextprotocol.io/specification/2025-03-26/server/tools)). OpenAI Agents SDK: одобрение «не гарантирует выполнения ровно один раз» ([OpenAI](https://openai.github.io/openai-agents-python/human_in_the_loop/)).
- **Механизм:** приложение объявляет класс каждого порта инструмента на доверенной стороне; подсказка этого никогда не заменяет. Ключи выдаёт только runtime. R14 ограничивает итоговый статус задачи знанием о её вызовах; текст модели не может его повысить.
- **Правило:** [§2.6](../../spec/ballarch-core-2.0.md#26-declaring-effect-classes), R8, R14, R15.
- **Доказательства здесь:** `KnowledgeTest` и перебор примера с поездкой (P12). Эталонного кода агента в репозитории нет.
- **Новизна:** модель как советчик за детерминированной политикой — не новость. Её связка с итоговым отчётом, который вычисляет алгебра, — это сочетание.

### P9. Код меняется, пока работа не завершена

- **Где встречается** (дата обращения: 2026-10-27): workflow Temporal с автоматическим обновлением «нужно вручную поддерживать безопасными для воспроизведения (replay)» ([Temporal](https://docs.temporal.io/worker-versioning)). Inngest выполняет переименованный шаг заново ([Inngest](https://www.inngest.com/docs/learn/versioning)). Во время постепенного развёртывания Cloudflare Durable Objects работают в разных версиях ([Cloudflare](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/with-durable-objects/)).
- **Механизм:** воспроизведения нет. Runtime хранит состояние и журнал вызовов и классифицирует каждый вызов по записанному классу. У типа Ball есть версия состояния и `migrate`. Runtime отказывается стартовать на записях, которые не может обслужить. Исключительное владение передаёт экземпляры от одного runtime к следующему.
- **Правило:** R4, R16, эволюция ([§6.1](../../spec/ballarch-core-2.0.md#61-evolution)).
- **Доказательства здесь:** `EvolutionTest`: `a call is classified by the effect class recorded at commit, not by the port's binding after a restart`. `OwnershipTest`: четыре теста, в одном из них участвует второй процесс.
- **Новизна:** не ново — восстановление без воспроизведения. Его ограничения описаны в [§10](../../spec/ballarch-core-2.0.md#10-trade-offs-and-known-limitations).

### P10. Сопоставление результатов, порядок и чередование оставлены коду приложения

- **Где встречается** (дата обращения: 2026-10-27): в Swift «функции, изолированные в акторе, реентерабельны», поэтому на каждом `await` может вклиниться другая работа ([SE-0306](https://github.com/apple/swift-evolution/blob/main/proposals/0306-actors.md)). Зёрна (grains) Orleans, которые вызывают друг друга, могут попасть во взаимоблокировку ([Orleans](https://learn.microsoft.com/en-us/dotnet/orleans/grains/request-scheduling)).
- **Механизм:** у каждого экземпляра — один шаг за раз. Ни один Ball не ждёт другого, поэтому цикл вызовов не может ни заблокироваться, ни повторно войти в решатель. Каждый вызов получает одно завершение, и оно доставляется экземпляру, который зафиксировал вызов. `CallRef` в состоянии указывает, какое завершение может изменить экран.
- **Правило:** R3, R6, [§3.4](../../spec/ballarch-core-2.0.md#34-ball-to-ball-calls).
- **Доказательства здесь:** свойства трассы T3 и T6; `InlineSchedulerTest`; `CatalogSearchTest`: `only the latest search changes the display, which a typed watch shows`.
- **Новизна:** не ново — акторы, Elm, The Composable Architecture.

### P11. Двойную отправку решают заново на каждом экране

- **Где встречается** (дата обращения: 2026-10-27): `bloc_concurrency` предлагает преобразователи событий `droppable` и `restartable` ([pub.dev](https://pub.dev/packages/bloc_concurrency)). У каждого фреймворка своя политика.
- **Механизм:** решает стадия Ball. Повторный запрос «place» застаёт стадию `Placing` и присоединяется к ней. Внешний запрос с тем же ключом идемпотентности присоединяется к первому или повторно получает его ответ. «Побеждает последний» — это `Cancel` плюс проверка `CallRef`. DSL допуска нет.
- **Правило:** R1, входящие запросы ([§3.3](../../spec/ballarch-core-2.0.md#33-inbound-request-lifecycle)).
- **Доказательства здесь:** `PlaceOrderTest`: `decide places a new order, joins a double tap, and repeats an unknown one with its intent`. `RuntimeTest`: `same key with a different message is an idempotency conflict`.
- **Новизна:** польза для внедрения, а не исследовательский результат.

### P12. Долгие процессы заявляют успех или неудачу после частичного эффекта

- **Где встречается** (дата обращения: 2026-10-27): процесс, разнесённый по уведомлениям о событиях, «не выражен явно ни в одном тексте программы» ([Fowler](https://martinfowler.com/articles/201701-event-driven.html)). Oxide: сага «может откатиться, оставив экземпляр работающим», а неудачная отмена оставляет её в состоянии `Stuck` ([Oxide RFD 704](https://rfd.shared.oxide.computer/rfd/0704)).
- **Механизм:** Flow — это один Ball, состояние которого и есть процесс. Значение знания (all, any) в трёхзначной логике Клини ограничивает то, что Flow может утверждать. Вызовы, которые он ещё может сделать, считаются `Maybe`; отменой считаются только поглощающие компенсации. Завершённый Flow отвечает своим знанием, как один честный вызов.
- **Правило:** R14, знание ([§4.2](../../spec/ballarch-core-2.0.md#42-knowledge-of-composite-operations)), замыкание ([§7.4](../../spec/ballarch-core-2.0.md#74-composition-closure)).
- **Доказательства здесь:** `KnowledgeTest` проверяет корректность и точность на 69 905 мирах. `TripFlowTest`: в 6438 прогонах ни один статус и ни одно утверждение о завершённой операции не противоречили бронированиям, а двузначный статус ошибся в 1190; без отсечения у провайдеров 115 из 7257 завершённых прогонов заканчиваются ложным утверждением. `ItineraryFlowTest`: ни одного ложного утверждения в 29 774 прогонах со сбоями и падениями и в 130 321 прогоне без падений.
- **Новизна:** новое применение классической структуры — главное заявление о новизне (строка 1).

### P13. С уведомлениями, которые теряются и дублируются, работают как с доставленными ровно один раз

- **Где встречается** (дата обращения: 2026-10-27): ошибки в последних битах кадра CAN могут приводить к несогласованной доставке и дубликатам (Rufino et al., 1998, [аннотация](https://www.dpss.inesc-id.pt/~ler/pubs/canamp.html)). AUTOSAR E2E с помощью счётчика обнаруживает данные `REPEATED` и `OKSOMELOST` ([AUTOSAR](https://www.autosar.org/fileadmin/standards/R22-11/FO/AUTOSAR_PRS_E2EProtocol.pdf)).
- **Механизм:** у вызова одно завершение; запоздавшие отчёты отбрасываются. Уведомления (notices) от одного издателя применяются по порядку и не более одного раза. Прерывание — подсказка прочитать статус, а не исход.
- **Правило:** R6, уведомления ([§3.6](../../spec/ballarch-core-2.0.md#36-notices)), C6.
- **Доказательства здесь:** S6 (`notices are delivered exactly once in order across a crash anywhere`); свойство трассы T6; тестбенч RTL ловит `MUTANT_NO_TAG_CHECK` и `MUTANT_DOUBLE_COMPLETION`.
- **Новизна:** не ново — счётчики последовательности и теги. Одно правило на трёх уровнях — часть строки 4.

### P14. У очередей офлайн-записи нет семантики исходов

- **Где встречается** (по состоянию на 2026-10-27): Updater в Store5 оставляет неудавшуюся запись «в очереди для будущих повторов», а его документация не говорит, могла ли эта запись уже быть применена ([Store5](https://store.mobilenativefoundation.org/docs/concepts/store5/updater)).
- **Механизм:** повторы runtime покрывают короткую недоступность до дедлайна вызова, а дедлайн должен укладываться в окно. При долгой недоступности намерение остаётся в стадии ожидания в очереди. После `Unknown` Ball повторяет вызов с тем же намерением внутри окна, а за его пределами выполняет сверку.
- **Правило:** намерения (§3.2), окна (§3.5), R15.
- **Доказательства здесь:** `PlaceOrderTest`: `a week later the deduplication window refuses to try again, and nothing is sent`.
- **Новизна:** часть скромного сочетания из строки 3. Слияние офлайн-правок — вне области применения.

### P15. Инварианты, охватывающие нескольких владельцев, и размывающиеся границы модулей

- **Где встречается** (дата обращения: 2026-10-27): в примере DCB с записью на курсы правилу вместимости, которое охватывает несколько агрегатов, нужна сага, и одна подписка записывается дважды ([DCB](https://dcb.events/)). Ретроспектива Packwerk: нарушения росли с каждой фичей, а пакет без нарушений всё равно не работал изолированно ([Rails at Scale](https://railsatscale.com/2024-01-26-a-packwerk-retrospective/)).
- **Механизм:** границы модулей — это проверки R10 в сборке. Для инвариантов между владельцами механизма нет: см. ниже.
- **Правило:** R10.
- **Доказательства здесь:** `featuresUseOnlyPublicApis` и `checkModuleBoundaries` в сборке Kotlin.
- **Новизна:** не ново — архитектурные тесты.

## Проблемы, которые Ballarch не решает

- **Офлайн-слияние** параллельных правок явно не входит в цели ([§1](../../spec/ballarch-core-2.0.md#1-scope)).
- **Инвариантам, охватывающим нескольких владельцев,** нужен координирующий Ball, резервирование или ограничение в хранилище.
- **Получатели, которые нарушают объявленный горизонт.** Статусу, прочитанному после горизонта доставки, доверяют. Негативный контроль S10 в `ReconciliationTest` должен найти ложный `NotDone` от получателя, который применяет запрос после своего горизонта.
- **Честность адаптеров и объявлений.** Проверки C1–C5 работают с симулированным получателем. C6, отображение реальных ответов, границы владения, классы эффекта, окна и горизонты требуют ревью.
- **Консенсус, репликация и горячие ключи.** Один владелец — это один последовательный писатель.
- **Эффекты ровно один раз (exactly-once).** Для эффекта «фактически один раз» (effectively-once) нужен получатель с дедупликацией или сверка.
- **Знание после падения в профиле Transient.** В `TripFlowTest` (`the trip requires the Durable profile`) клиент, который после перезапуска бронирует заново, получает ложное утверждение о завершённой операции в 608 из 3073 завершённых прогонов, а в 152 прогонах рейс бронируется дважды.
- **Исключение между хостами.** Блокировка файлового хранилища действует в пределах одного хоста.
- **Уровни вместе.** Ни одна проверка не охватывает прошивку за портом сервиса.
- **Другие языки.** Эталонный код есть на Kotlin, C и SystemVerilog. Для Swift, Rust и TypeScript есть только наброски ([привязки](bindings.md)).
- **Собственные издержки.** В профиле Durable один вызов с эффектом, получивший ответ `Done`, требует трёх долговечных записей (`RuntimeTest`). Выделенный цикл добавляет передачу между потоками на каждый вход. Продуктивность, размер кода и польза для агентов не измерялись.
