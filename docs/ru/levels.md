# Ballarch на каждом уровне

Правила исходов Ballarch не упоминают ни язык, ни транспорт, ни хранилище. Здесь они прочитаны для аппаратных блоков, прошивки, драйверов устройств и фреймворков для драйверов. Руководство информативное и расширяет [Core §11](../../spec/ballarch-core-2.0.md#11-interpretation-across-levels-informative); сами правила — в Core §2–§7. Структура мобильных и серверных приложений описана в руководстве [«Структура приложения»](structure.md).

У частей с пометкой «Набросок» нет эталонного кода, и соответствие для них не заявляется. Внешние факты пронумерованы [1], [2], … и перечислены в разделе [«Источники»](#источники).

## Что не меняется от уровня к уровню

Правила фиксации и исходов (R4–R8) и правило знания (R14) везде одинаковы. Каждый вызов заканчивается исходом `Done`, `NotDone` или `Unknown`, а для `NotDone` нужно доказательство неприменения (R7). Какие структурные правила применимы, зависит от того, какие элементы есть на уровне: в блоке без отложенных ответов правилу R9 нечего проверять ([Core §9.4](../../spec/ballarch-core-2.0.md#94-conformance-at-other-levels)).

На любом уровне задайте пять вопросов:

1. **Владелец:** какой единственный Ball меняет это состояние (R1)?
2. **Горизонт фиксации:** когда решение и запрошенные им эффекты впервые существуют вместе (R4, R5)?
3. **Горизонт отправки:** с какого момента запрос мог уйти (R7, R8)?
4. **Класс эффекта:** повтор безвреден (Safe), получатель его дедуплицирует (Idempotent) или он может срабатывать каждый раз (NonIdempotent; это значение по умолчанию, если есть сомнения)?
5. **`Unknown`:** какое доказательство его разрешит и кто это доказательство соберёт?

Idempotent здесь имеет узкий смысл из [Core §2](../../spec/ballarch-core-2.0.md#2-model): получатель узнаёт повтор по ключу, который несёт каждая попытка. Запись, которая просто устанавливает значение, — NonIdempotent: запоздавшая попытка может перезаписать более поздний запрос. Если такая запись закончилась `Unknown`, пишите снова, только когда чтение значения, сделанное после горизонта доставки, показывает, что запись не применена (R15).

## Синхронная аппаратура (RTL)

| Понятие | В тактируемой схеме |
|---|---|
| Владелец | единственный процесс `always_ff`, который пишет регистр; два писателя — ошибка множественного драйвера (multi-driver) |
| Решатель | один блок `always_comb` со значением по умолчанию для каждого сигнала; выведенная защёлка (inferred latch) — скрытое состояние |
| Горизонт фиксации | фронт тактового сигнала |
| Горизонт отправки | рукопожатие `valid && ready` на шине, где ведущее устройство (master) может отозвать непринятый запрос; на AXI, где VALID отзывать нельзя [6], — выставление VALID |
| Ключ идемпотентности | идентификатор команды, который несёт каждая попытка; тег {идентификатор команды, попытка} не используется повторно в пределах окна ответа, в том числе после сброса |
| `Unknown` | на принятую транзакцию нет ответа к дедлайну |
| Профиль | Transient: регистры не переживают сброс |

В [эталоне RTL](../../reference/rtl/README.md) два блока. Блок команд (issuer) отправляет READ (Safe), CONFIG (Idempotent, дедупликация по идентификатору команды) и FIRE (NonIdempotent). Проверка его параметров работает как окно дедупликации: каждый повтор доходит до устройства, пока оно ещё помнит идентификатор команды. Составной блок (composite) выполняет «настроить, затем запустить» и хранит знание об операции (all, any) в регистре состояния, по два бита на координату; регистр описывает операции после последнего сброса.

Yosys проверяет единственность драйвера (R1), триггеры как единственное хранилище (R2), один передний фронт тактового сигнала (R4) и регистровые выходы (R5). Тестбенч блока команд прогоняет 8764 сценария при каждом из трёх наборов параметров, а тестбенч составного блока — 1458 (числа печатают `tb_issuer.sv` и `tb_composite.sv`). Каждая из 28 внесённых ошибок должна приводить к падению тестбенча.

## Прошивка

[Эталон на C](../../reference/c/README.md) — runtime в профиле Durable для одного Ball на микроконтроллере:

- Горизонт фиксации: одна запись с проверкой CRC в одном из двух слотов NVM. Если запись оборвётся на середине (torn write), предыдущая запись останется действительной.
- Горизонт отправки: упреждающая запись (write-ahead), которая помечает попытку как *Sending* до вызова `transmit`.
- Запись каждого вызова хранит класс эффекта, который был у его порта на момент фиксации, и runtime классифицирует вызов по этому классу, в том числе после обновления ([Core §6.1](../../spec/ballarch-core-2.0.md#61-evolution)).
- Ключ вызова служит ключом идемпотентности. Ключи повторяются, только когда 32-битный ключ переполняется после достаточного числа зафиксированных решений или когда слоты стираются, поэтому с обновлением, которое их стирает, нужна осторожность ([Core §10](../../spec/ballarch-core-2.0.md#10-trade-offs-and-known-limitations)).
- Решатель — чистая функция `step()` в отдельной единице трансляции. Его проверяет линтер; эта проверка необходима, но не достаточна.
- Износ: каждая фиксация и каждая упреждающая запись переписывают всю запись в другом слоте. Вызов с эффектом стоит трёх записей в NVM плюс одну на каждый повтор ([Core §10](../../spec/ballarch-core-2.0.md#10-trade-offs-and-known-limitations)), и столько же эталон тратит на Safe-вызов ([`test_runtime.c`](../../reference/c/test/test_runtime.c), тег `wear`). Выберите носитель, ресурс которого выдерживает такую частоту записи, или спрячьте выравнивание износа (wear levelling) за `nvm_write`; эталон только чередует два слота.

Полный перебор в заданных границах ставит по одному сбою в каждую точку отключения питания и каждую запись в NVM и перебирает исходы связи для первых передач. В границах по умолчанию он проходит 937 229 прогонов дозатора и 982 599 прогонов перекачки без нарушений; при любом другом итоговом числе тесты падают. Алгебра на C проверена на тех же 69 905 мирах, что и алгебра на Kotlin. В эталоне нет Cancel, намерений (intents), окон дедупликации, тайм-аутов попытки, портов со сверкой и чтений с ревизией.

## Драйверы

Ball драйвера — состояние одной пары очередей или одного протокола устройства: таблица незавершённых команд с их фазами. Обработчик прерывания — входящий адаптер: он передаёт завершения владельцу и ничего не решает. Память драйвера — Transient, а сброс устройства — отказ получателя, который владелец переживает.

| Понятие | В драйвере |
|---|---|
| Горизонт фиксации | запись в журнале вызовов и дескриптор, сделанные, пока устройство их не видит |
| Горизонт отправки | первая запись, на которую устройство может отреагировать: флаг владения в опрашиваемом кольце, `writel()` в doorbell или запрос на передачу CAN. В руководстве ядра по барьерам памяти запись дескриптора упорядочена перед записью его флага владения с помощью `dma_wmb()`, а затем идёт запись в doorbell через `writel()` [1]. `writel_relaxed()` не упорядочен после записей в DMA-память [2], и писать им в этот doorbell нельзя [3]: это правило для линтера. |
| Завершение | запись в очереди завершений, регистр состояния или кадр ответа: отчёт адаптера |
| Прерывание | подсказка прочитать источник завершений, а не уведомление, которое приходит ровно один раз. Это чтение — Safe, только если оно ничего не меняет. Чтение статуса, которое его сбрасывает (read-to-clear), или подтверждение прерывания — NonIdempotent (см. «Классы регистров» ниже): делайте это один раз, в адаптере, и сообщайте прочитанное значение. |
| Дедлайн | сначала опросите источник завершений. Драйвер NVMe в Linux в обработчике тайм-аута опрашивает очередь завершений, прежде чем прервать команду или выполнить сброс [4] |
| Сброс | сначала снимите статус: сброс стирает доказательства |
| После сброса или AER | каждая команда в фазе `Sending` — `Unknown`, если её доказательство не сохранено; так и не опубликованная команда — `NotDone` |
| Совет о повторе | бит DNR в NVMe означает «не повторять» [5], а не «ничего не применено»; коды «занято» (busy) и «попробуйте снова» (try again) — тоже советы о повторе |
| Теги | не используются повторно в пределах окна ответа, в том числе после сброса |

Набросок: эталонного кода нет, соответствие не заявляется.

```c
q->pending[tag] = (struct pending){ .phase = PENDING, .req = *req };
d->addr = req->dma; d->len = req->len; d->tag = tag;   /* commit horizon: not yet visible */
q->pending[tag].phase = SENDING;   /* write-ahead: possibly sent from here on */
dma_wmb();                         /* descriptor contents before ownership */
d->status = DEVICE_OWN;            /* a polling device may start here */
writel(q->tail, q->doorbell);      /* never writel_relaxed() here */
```

**Классы регистров** ([Core §2.6](../../spec/ballarch-core-2.0.md#26-declaring-effect-classes)):

| Доступ | Класс |
|---|---|
| чтение статуса без побочного эффекта | Safe |
| запись, которую устройство дедуплицирует по тегу или идентификатору команды, который несёт каждая попытка | Idempotent |
| абсолютная запись конфигурации без такого тега | NonIdempotent |
| чтение со сбросом (read-to-clear), сброс записью единицы (write-1-to-clear), запись в FIFO или чтение из него, подтверждение прерывания чтением, doorbell, стартовый бит, программирование или стирание flash, импульс на исполнительный механизм | NonIdempotent |

**Что получает разработчик драйверов:**

1. Одно правило, которое по фазе и классу делит `-EIO` и `-ETIMEDOUT` на `NotDone` и `Unknown`, на любой шине.
2. Механические повторы: только для Safe- и Idempotent-доступа и только силами runtime.
3. Записанные правила восстановления: сначала опрос, снятие статуса до сброса, никакого повторного использования тегов в пределах окна, `Unknown` после сброса.
4. Отмена, которая утверждает не больше, чем доказывает устройство; один контроллер CAN может подтвердить отмену кадра, который продолжает передавать [9].
5. Чистый шаг, который можно перебрать на хост-машине со сбоем в каждой точке отключения питания и каждой записи в NVM, как в эталоне на C.
6. Слово состояния, по два бита на координату, для многошаговой работы: стирания, программирования, проверки и переключения образа (swap). Тестбенч составного блока RTL проверяет, что такое слово ни в одном из прогоняемых сценариев не утверждает лишнего.
7. Карантин одного экземпляра вместо цикла перезагрузок, когда запись нельзя использовать ([Core §6.1](../../spec/ballarch-core-2.0.md#61-evolution), пункт 3).
8. Общий словарь с командой приложения: `Unknown` устройства может дойти до пользователя как «проверяем». Ни один эталон не соединяет уровни, поэтому этот путь ничем не проверен.

## Отображение на фреймворки

Набросок: эталонного кода нет, соответствие не заявляется.

| Фреймворк | Куда помещается Ball | Что добавить |
|---|---|---|
| Активные объекты QP | активный объект уже обрабатывает каждое событие до конца (run-to-completion) и обменивается событиями вместо общих данных [11] | журнал вызовов с фазами; фиксация до отправки события, которое уходит наружу |
| RTIC | состояние Ball как ресурс `#[local]`, доступный только его задаче [12] | обработчики прерываний отправляют отчёты этой задаче |
| Embassy | одна задача владеет runtime и периферией, переданной ей при запуске (spawn) [13] | адаптеры в виде future, которые сообщают о результате; уничтожение (drop) такой future — не доказательство |
| Zephyr | класс каждого порта как свойство devicetree, которое задаёт приложение, а не производитель платы (из bindings генерируются макросы C [14]) | таблица перевода errno в исходы для каждого драйвера; `i2c_transfer()` сообщает об ошибке как `-EIO` [15], и для записи с эффектом это `Unknown` |
| Tock | `Ok` от вызова в две фазы (split-phase) значит, что последует callback, а `Ok` от отмены говорит, удалось ли отменить (TRD 3 [16]) | классы эффекта и `Unknown` |
| Linux | состояние каждой очереди под одной блокировкой или в одной workqueue; обработчик прерывания передаёт ей завершения | фреймворк не предлагается |

## Таблицы исходов протоколов

Каждая строка сопоставляет то, что видит отправитель, с исходом запроса с эффектом; Safe-запрос без ответа заканчивается `NotDone(NoAnswer)` ([Core §3.2](../../spec/ballarch-core-2.0.md#32-call-lifecycle)). Строки без проверенного первичного источника помечены *не проверено*.

**AXI** [6]

| Отчёт | Исход |
|---|---|
| VALID выставлен (§A2.3): до рукопожатия его нельзя снять | горизонт отправки |
| `OKAY` на неэксклюзивную запись (таблица A3.28) | `Done` |
| `SLVERR`: запрос дошёл до конечной точки, но не выполнился; данные по адресу могли обновиться частично | `Unknown` |
| `DECERR`: запрос не дошёл до точки, где данные можно записать; данные по адресу могли обновиться частично | `Unknown` |
| `DEFER`, `UNSUPPORTED` (только WriteDeferrable): данные по адресу не обновлены | `NotDone` |
| нет ответа к дедлайну | `Unknown` |

**AXI firewall** (AMD PG293 [7])

| Отчёт | Исход |
|---|---|
| ответ об ошибке, который блокирует firewall; его команда уже дошла до защищаемой стороны | исход этого ответа (`Unknown` для `SLVERR`) |
| `SLVERR`, который выдаёт сам firewall, сбрасывая (flush) незавершённые транзакции | `Unknown`: ответ сформировал firewall, а не устройство |

**PCIe**

| Отчёт | Исход |
|---|---|
| posted-запись: завершения нет | `Unknown`, пока не вернётся последующее чтение с того же устройства: оно показывает, что запись дошла [2] |
| фатальная некорректируемая ошибка: Linux выполняет вторичный сброс шины (secondary bus reset) [8]; при необратимом отказе драйверы завершают ожидающий ввод-вывод с `-EIO` [10] | `Unknown` для каждой команды, которая могла быть отправлена; `NotDone` для так и не опубликованной |
| non-posted запрос без завершения до истечения Completion Timeout | `Unknown` (*не проверено*) |
| завершение со статусом Unsupported Request или Completer Abort | *не проверено* |

**NVMe**

| Отчёт | Исход |
|---|---|
| тайм-аут | опросите очередь завершений [4]; найденное завершение и есть ответ; иначе abort или сброс, а для записи — `Unknown` |
| статус ошибки с установленным DNR | не повторять [5]; исход по коду статуса — *не проверено* |
| сброс контроллера при незавершённых командах | `Unknown` для каждой незавершённой записи |
| завершение команды Abort | *не проверено* |

**CAN**

| Отчёт | Исход |
|---|---|
| запрос на передачу выставлен | горизонт отправки |
| отмена подтверждена | `Unknown`. По состоянию на 2026-10-27 в errata Microchip для SAMA7G5 описано, что кадры CAN FD с более чем 8 байтами данных передаются целиком после подтверждённой отмены [9] |
| передача завершена | кадр дошёл до шины, а не до приложения получателя. Ошибки в последних двух битах конца кадра (end-of-frame) могут приводить к дубликатам и несогласованной доставке [17], поэтому NonIdempotent-команде нужен идентификатор команды, по которому получатель её дедуплицирует |
| bus-off при ожидающем кадре | *не проверено* |

**I2C и SPI** (коды ошибок Linux [18])

| Отчёт | Исход |
|---|---|
| `EINVAL`: недопустимый параметр обнаружен до начала ввода-вывода | `NotDone` |
| `ESHUTDOWN`: адаптер приостановлен | `NotDone` |
| `ENXIO`: на фазе адреса не пришёл ACK | `NotDone` для записи из одного сообщения; `Unknown`, если предыдущие сообщения могли выполниться |

| ошибка SPI после начала передачи; в SPI нет подтверждений | `Unknown` (*не проверено*) |

## Уровни без эталонного кода

Эти строки показывают, как отвечать на пять вопросов, а не то, что какой-либо продукт соответствует Ballarch; ни одна проверка здесь их не покрывает.

| Уровень | Владелец | Горизонт отправки | `Unknown`, если |
|---|---|---|---|
| Очереди GPU | одна аппаратная очередь | обновление указателя записи | сброс, пока задания выполняются |
| Сетевые стеки | одно соединение | копирование в буфер сокета | сброс соединения после него; подтверждение относится к сетевому стеку собеседника, а не к его приложению |
| Задачи RTOS | одна задача на протокол устройства | запись, которая запускает передачу | сброс по watchdog после неё |
| ПЛК | программа, которая пишет выход | образ выходов или кадр полевой шины | относительное перемещение без подтверждения |
| Базы данных | Ball клиента | `COMMIT` в сокете | соединение оборвалось до ответа |
| Смарт-контракты | отправитель вне блокчейна | рассылка транзакции в сеть (broadcast) | транзакция ещё не стала окончательной |

Ни один эталон не соединяет уровни. Ни одна проверка не покрывает прошивку, которая управляет RTL-блоком как Ball за портом, или сервис, который обслуживает прошивка ([Core §10](../../spec/ballarch-core-2.0.md#10-trade-offs-and-known-limitations)).
